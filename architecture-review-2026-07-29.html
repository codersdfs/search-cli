After — one Search module, trending as an adapter strategy

Problem: The Trending module (526 lines) is a parallel fetch path that scrapes HTML from github.com/trending, parses it into TrendingRepo[], then converts each to Repo via trendingRepoToRepo. The Search module (555 lines) fetches from the GitHub API, normalizes to Repo[], and ranks. Both paths are consumed by cli.ts, watch.ts, and tui.ts — three call sites each import from both modules. The TrendingRepo type is a near-duplicate of Repo with starsToday and rank added. The conversion function trendingRepoToRepo is duplicated logic that fills in fake values (forks: 0, watchers: 0, createdAt: "") for fields the HTML scrape doesn't provide.

Solution: Collapse trending into the Search module as a second adapter. Add a TrendingSearchAdapter that implements SearchAdapter — it scrapes HTML, parses, and returns SearchResponse directly. The TrendingRepo type disappears; trending repos become Repo objects with score carrying the star-growth value (already used in tui.ts line 1531). The trendingRepoToRepo conversion function is deleted. The SearchModule already has the adapter seam — this is a real seam with three adapters (GitHub API, GitHub Trending HTML, in-memory).

  • • locality: both fetch paths in one module, not scattered across 2 files
  • • leverage: one adapter seam, 3 implementations — call sites use one interface
  • • interface: 3 call sites × 2 imports → 1 import from Search module
  • • tests: trending adapter tested via in-memory adapter, no HTML fixture needed for integration
  • • deletion: removes trendingRepoToRepo, TrendingRepo type, and the duplicate Repo conversion

Problem: Six modules each independently call mkdirSync, readFileSync, writeFileSync, and stateDir() from config.ts. The file I/O pattern is duplicated with minor variations (JSON vs JSONL, append vs overwrite, sort vs unsorted). This is a classic local-substitutable seam — the same logic repeated, just with different filenames.

Solution: Extract a single persistence adapter with readJSON<T>(path), writeJSON(path, data), appendJSONL(path, obj), and stateDir(). Each domain module becomes a thin wrapper that delegates I/O to the adapter. The adapter is the seam — swap it for an in-memory implementation in tests.

  • • leverage: one I/O implementation, 6 call sites
  • • locality: file I/O bugs (permissions, race conditions) fix in one place
  • • tests: swap adapter for in-memory, no temp files needed
  • • interface: 6 modules × 3 fs calls → 1 adapter with 4 methods

Problem: export.ts and pipe.ts are two shallow modules that both implement a switch on a format string. export.ts handles JSON/CSV/Markdown/text; pipe.ts handles urls/names/ssh-urls/clone-commands/ids. Both have a formatX function per format and a dispatcher. The interface (format string) is nearly as complex as the implementation (8 format functions). cli.ts imports from both.

Solution: Collapse into one Output module. Use a registry: const FORMATS = new Map<Format, (repos) => string>(). Both export and pipe formats register in the same map. One format(repos, format) function dispatches. exportToFile and pipeExec become methods on the same module.

  • • leverage: one format registry, one dispatcher
  • • interface: 2 modules × 7 functions → 1 module with registry
  • • locality: adding a new format = 1 line in the registry, not 2 files
  • • tests: test format registry directly, no cli.ts needed

Problem: tui.ts is 2000+ lines and directly imports 14 modules. It mixes rendering logic with state management, domain calls, and event handling. Understanding the TUI requires bouncing between tui.ts, deepdive.ts, compare.ts, explore.ts, and trending.ts.   • • interface: 14 imports → 1 SearchState import in the view
  • • tests: SearchState is testable without OpenTUI renderer
  • • caution: OpenTUI's renderer is tightly coupled to component lifecycle — may need adapter for testability

Problem: cli.ts's runNonInteractive function has 6 branching paths (trending, watch, pipe, format, count, standard search). Each branch independently calls applyFlagFilters(parseQuery(query), {}), builds SearchOptions, calls provider.search, and calls rankRepos. The query parsing and options construction is duplicated 4 times. The trending path is entirely separate from the search path, even though both produce Repo[].

Solution: Collapse the 6 branches into a dispatch table. Extract the shared setup (parse query, build options, create provider) into one function. Each handler receives the parsed query and options, and returns Repo[] or SearchResponse. The trending handler uses the trending adapter; the search handler uses the GitHub adapter. Both return Repo[] from the same interface.

  • • locality: query parsing in one place, not duplicated 4 times
  • • interface: 6 branches → 1 dispatch with shared setup
  • • tests: each handler testable independently with in-memory adapter
  • • deletion: removes 4 copies of applyFlagFilters(parseQuery(query), {})

Top recommendation

Collapse the Trending module into the Search module (Candidate 1).

The Search module already has the adapter seam (SearchAdapter interface, GitHubSearchAdapter, InMemoryAdapter). The Trending module is a parallel fetch path that produces the same Repo[] output but through a different adapter (HTML scrape vs API). The deletion test passes — collapsing these concentrates the fetch logic into one deep module rather than spreading it across 2 files. Three call sites (cli.ts, watch.ts, tui.ts) each import from both modules; unifying them behind the existing adapter seam eliminates the duplicate trendingRepoToRepo conversion and the TrendingRepo type. The SearchModule already caches responses — trending repos would benefit from the same caching without any new code.
