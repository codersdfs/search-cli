# v9.10.0

ghfind's TUI has always been keyboard-only — and, quietly, half-broken for the
mouse. OpenTUI was already emitting SGR mouse tracking and hit-testing every
event into a target renderable. Nothing in ghfind consumed any of it. The
events were parsed, dispatched, and thrown away. This release makes the TUI
clickable, and fixes the two keyboard rough edges that were hiding behind it.

## The TUI is now fully clickable

Click a result and the detail pane updates. Click it again and your browser
opens. Scroll to move through results. Click outside an overlay to close it.

Every list, card, tab and button responds: the results list, the landing mode
cards, trending tabs, the update dialog's buttons, and every overlay list
(history, bookmarks, saved searches, topics, export, share, and the command
menu itself).

The important detail is that clicks do not reimplement anything. A click calls
`setSelectedIndex`, which emits the same `selectionChanged` event `↑`/`↓`
already emitted, so the detail pane, the detail graph and the packages view all
work identically without a parallel code path. A double-click calls the same
activation path as `Enter`. There is no mouse branch to keep in sync — the
keyboard and the mouse converge on one implementation, which is also why they
cannot drift.

## The wheel scrolled the wrong pane

Worth calling out, because it predates this release and was a real bug rather
than a missing feature.

When a scroll event hit nothing, OpenTUI falls back to delivering it to
whatever renderable currently holds focus. In ghfind that was almost always the
results list. So opening the README viewer and scrolling would move the
_result selection_ instead of the README — the one thing you were trying to do.

Every scrollable region now claims the wheel explicitly, and the list's wheel
handler steps the selection through `moveUp`/`moveDown`, so wheel navigation
and `↑`/`↓` navigation cannot diverge either.

## Text that swallowed clicks

`TextRenderable` defaults to OpenTUI's `selectable: true`, and a left-press on
a selectable renderable is consumed as a text-selection drag _before_ the app's
own handlers run. The detail pane, comparison table, tab bar and other read-only
text are all `TextRenderable`s, so clicks landing on them did nothing at all.

They now opt out of text selection. The query input deliberately keeps it, so
clicking into the input still places your cursor.

## A hover highlight that painted the list magenta

Small one, but it would have been immediately obvious to anyone using it.
OpenTUI's colour parser accepts `"transparent"`, CSS colour names, and 3/4/6/8
digit hex — nothing else. An `rgba(255,255,255,0.06)` hover tint failed that
check and fell through to its magenta fallback, so hovering a list would have
flashed it magenta. Now written as `#ffffff0f`.

Found because the test harness prints that warning. Worth noting the class of
bug: OpenTUI degrades an invalid colour to magenta rather than throwing, so this
fails silently and visibly at the same time.

## `Space` opened the menu only if you had clicked something first

The subtlest problem in this release, and it was not caused by mouse support —
it was exposed by it.

The query input is focused by default. The command menu was bound to `Space`,
gated on the input _not_ being focused, so that spaces could still be typed into
a query. That gate meant `Space` opened the menu only when focus had moved
somewhere else. The one way focus moved was clicking a result row: OpenTUI's
auto-focus-on-press walks up from the pressed renderable to the nearest
focusable ancestor, finds the results list, and focuses it — blurring the input
as a side effect.

So on a fresh launch, `Space` typed a space. Click any row, and `Space` opened
the menu. Same key, same screen, different behaviour depending on invisible
state.

A regression test now pins this down from both directions: with `keepFocus` a row
click does not move focus, and without it one does.

The resolution is that **`Esc` opens the command menu**, and `Space` always
types. `Esc` already closed every overlay, so this adds a meaning rather than
replacing one. For anyone who prefers not to reach for `Esc`, there is now a
<kbd>☰ menu</kbd> button in the bottom-right corner — clickable, it floats above
the layout, and it hides while an overlay is open so it never sits on top of one.

## Added

- Full mouse support: click to select, double-click to open, wheel to scroll,
  click-outside to dismiss, hover feedback with a pointer cursor.
- <kbd>☰ menu</kbd> button in the bottom-right corner to open the command menu.
- A "Mouse" section in the in-app help, documenting every binding.
- README keybinding tables gained a mouse table; the command-menu references
  across the README and `docs/HOW-TO.md` now say `Esc` instead of `Space`.

## Fixed

- The scroll wheel scrolled the focused renderable rather than the pane under
  the pointer, so long-pane scrolling moved the result selection instead.
- Non-interactive text consumed left-presses as text-selection drags, so clicks
  over the detail pane and comparison table did nothing.
- The hover tint used an `rgba()` string that OpenTUI's colour parser rejects,
  rendering the list magenta.
- `Space` could not open the command menu on a fresh launch, because it was
  gated on focus that only moved after a mouse click.

## Verification

The suite grew by 33 tests, to 657.

- **15 unit tests** on the click→row geometry: scroll offsets, multi-line rows
  (overlay lists render a description line, so each option is two lines tall),
  `itemSpacing`, clicks past the last row, unmeasured renderables, and empty
  lists. OpenTUI keeps `scrollOffset` and `linesPerItem` private, so this
  arithmetic is read through a single narrow cast — the tests are what keep that
  cast honest.
- **12 integration tests** driving the real handlers with OpenTUI's mock mouse
  against a live renderer: click-selects, double-click-opens, the double-click
  window expiring, click-outside dismissal, row clicks _not_ leaking to the
  enclosing panel, focus behaviour with and without `keepFocus`, and wheel
  stepping including both ends of the list.
- **4 button tests** asserting the corner button actually lands in the
  bottom-right, that hidden buttons neither render nor take clicks, and that its
  click does not bubble.

The first two geometry tests failed on the run that wrote them, and caught a
real off-by-one: the empty area below a short list returned "no row" instead of
resolving to the last row, which would have dismissed an overlay instead of
selecting its final entry. That is the exact class of bug that would have been
very annoying and very hard to report.

`test`, `format:check`, `lint` (Biome) and `typecheck` (tsc) are all green, and
`bun run build` succeeds. The TUI was also driven end-to-end in a pty to confirm
the menu opens from both `Esc` and the corner button, since the mock mouse does
not exercise a real terminal's mouse reporting.
