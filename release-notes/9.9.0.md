# v9.9.0

ghfind used to hand your query straight to GitHub: whatever you typed was
string-concatenated into an API URL. A misspelled qualifier or a malformed
value became an opaque `422` from GitHub, or — worse — a **"network error"**
naming a connectivity problem you did not have. This release makes ghfind
_understand_ the query before spending a request on it, and adds a
task-oriented guide for using it.

## A typo in a qualifier no longer ruins the search

`matchQualifier` accepted any word before a colon as a qualifier key, so
`langauge:Rust` was not treated as the typo it was — it was forwarded verbatim
and GitHub rejected it with an error that named nothing useful. Now:

```console
$ ghfind "cli langauge:Rust stars:10k"
# runs as: cli language:Rust stars:>=10000
```

Misspellings are corrected two ways: a table of common ones (`langauge`,
`star`, `licence`, `push`), plus a bounded edit-distance pass that catches the
rest (`starss` → `stars`).

**The correction is deliberately narrow.** It only touches the qualifiers
ghfind knows. `is:public`, `has:funding-file` and `props.environment:prod` are
valid GitHub syntax that ghfind has no business rewriting — and two real bugs
came from trying:

- `is` sits one edit from the known qualifier `in`, so an unguarded fuzzy pass
  turned `is:public` into `in:public`, which validation then rejected. Fuzzy
  correction is now skipped for keys under four characters.
- Ambiguous input (`sizet`) is left alone rather than rewritten arbitrarily —
  with two candidates equally close there is not enough signal to guess.

`props.*` had the opposite problem: custom-property keys contain a dot, which
the parser's key charset rejected, so `props.environment:production` silently
degraded into a literal keyword. The charset now allows one dot.

## A bad value fails before the request, naming the fix

Every qualifier now has a value rule — numeric counts for `stars`/`forks`/
`size`/`topics`/`followers`, booleans for `archived`, `true|false|only` for
`fork`, ISO8601 dates for `created`/`pushed`/`updated`, the `visibility:`
enum, and the `in:` searchable fields:

```console
$ ghfind "cli stars:abc"
⚠ Invalid query: "stars:abc" is not a number — use stars:100, stars:>=100, or stars:1k..10k
  Try: cli
```

Dates are checked against the calendar, not just the shape — `2024-02-31` and
`2023-02-29` are rejected, which `Date.parse` would have quietly rolled over.
Documented comma-lists like `in:name,description` and the `fork:only` form are
accepted, because rejecting a valid form is worse than passing a bad one
through.

## One gate, enforced everywhere

`validateQuery` existed but was called by **the TUI only**. The CLI, the MCP
server and `--watch` all skipped it, so the single rule it enforced
(`visibility:` + `private:`) applied in one of four places. All four now go
through it, and for agents a malformed query returns a readable message with
`invalidQuery: true` rather than a tool failure that reads as breakage.

`--watch` validates before its poll loop starts: a malformed query is not
transient, so retrying it five times just printed the same error five times.

## Counts: `10k` works, and `100` still means exactly 100

`stars:10k` → `stars:>=10000`, `size:1m` → `size:>=1000000`,
`stars:1k..10k` → `stars:1000..10000`.

A bare number is left alone, and that is the subtle part: GitHub reads
`stars:100` as _exactly_ 100 stars. Rewriting it to `>=100` — which a first
pass here did — silently changes the question being asked. Verified live:

    stars:100 language:Rust      -> 118 repos
    stars:>=10000 language:Rust  -> 256 repos

## Zero results now come with a way out

Previously: _"check spelling, try fewer qualifiers, or browse trending."_
Now ghfind ranks the qualifiers by how sharply each one narrows the corpus and
offers a concrete retry:

```console
🔍 No results for "rust stars:>=5000000".
  Try: rust stars:>=500000
```

A star or size threshold empties a result set outright, so those are loosened
first; a plain `language:` filter matches plenty on its own, so it is touched
last. Each suggestion rewrites one qualifier rather than dropping it, keeping
the retry a recognisable version of the original question. A negated filter is
never suggested for removal — it can only widen a search, so it cannot be what
emptied it.

## A 403 no longer claims SSO is the cause

Found while testing this: the TUI showed `Forbidden (403). If your org
enforces SSO…` and nothing else. Three unrelated conditions produce a 403 with
rate-limit budget remaining — SSO not authorizing the token, a secondary/abuse
rate limit, and org resource restrictions — and the message asserted the first
one unconditionally. For someone who was actually being secondary-rate-limited,
that sent them to fix a credential problem that did not exist.

The message now reports GitHub's own explanation and names both plausible
causes. To see which one it is, `GHFIND_LOG=<path>` writes diagnostics to a
file — the TUI owns the screen and cannot print them into it, and its logger
used to be a silent no-op, which is why this was undiagnosable in the first
place:

```
[debug] [github] request url: https://api.github.com/search/repositories?q=cli
[error] [github] non-rate-limit 403: remaining=42 retry-after=60
 x-ratelimit-reset=1790859999 authed=no url=…
[error] [github] 403 body: {"message":"Resource not accessible by integration"}
```

Unset by default, so it costs nothing in normal use; token values are redacted
from logged URLs.

## The post-upgrade panel never went away

The panel that says `Updated ghfind 9.8.3 → 9.9.0` is triggered by a single
condition: `lastInstalledVersion !== currentVersion`. Nothing in the codebase
ever wrote `lastInstalledVersion` back after showing the panel, so the
condition stayed true forever:

    launch 1 after upgrade:  panel shown
    launch 2:               panel shown again
    launch 3:               panel shown again
    …

Worse, dismissing it did not help. **later** writes `snoozeUntil` and **never**
writes `suppressed` — neither touches `lastInstalledVersion`, and the
post-upgrade panel's guard only checks `suppressed`. So a user who explicitly
told ghfind to stop notifying them still got the panel on every launch.

The panel now acknowledges itself once shown. Two guards keep that honest: a
recorded version _newer_ than the running one is left alone (so a rolled-back
install, or an update that landed mid-session, is still reported), and the
write is best-effort so a read-only state dir cannot block the panel.

Verified across a simulated six-launch sequence:

    panel per launch: [true, false, false, false, false, false]

## A prerelease was being advertised as an upgrade

`isNewerVersion` prefers `Bun.semver` and falls back to hand-rolled comparison
for Node and the compiled binaries. The fallback dropped the pre-release suffix
but compared nothing else about it, so `9.9.0` → `9.9.0-beta.1` reported
`true` — offering a **downgrade** as an update. Build metadata had a related
bug: `9.9.0+build.5` parsed `Number("0+build")` as `NaN`, silently becoming
`0`.

Comparison now follows npm ordering. A prerelease counts as an upgrade only when
its numeric core is genuinely ahead; within the same core, only a
prerelease → release move counts; build metadata is stripped before parsing.
The Bun path was already correct and is untouched.

## `forks` was silently the wrong qualifier

`KNOWN_QUALIFIERS` listed `fork` but not `forks`. So `forks:100` fell through
to fuzzy matching, got rewritten to `fork:100`, and skipped numeric validation
entirely — `forks:abc` validated clean and reached GitHub. `forks`, `topics`
and `followers` are now known, and `fork` (a boolean) stays distinct from
`forks` (a count).

## A how-to guide

`docs/HOW-TO.md` covers the task-shaped material the README does not: getting a
token in place first (60/hr → 5,000/hr is the difference between a TUI session
that works and one that dies mid-scroll), how to write a query, a qualifier
table, what to read in the results, what to do about an error, and copy-paste
recipes. Its claims are pinned by tests so the page cannot drift from the code.

## Verification

The suite grew by 110 tests: 82 for query parsing and validation, 2 pinning the
403 diagnostics, 11 keeping the how-to page honest, and 15 on self-update. The
new tests cover each qualifier value rule, `k`/`m` normalization and the
exact-match guarantee, misspelling correction and unknown-qualifier
passthrough, keyword-order and `raw` preservation, the relaxation ranking, the
403 diagnostics — including that `remaining: 0` still routes to
`RateLimitError` rather than `ForbiddenError` — and the update panel firing
exactly once across repeated launches.

`format:check`, `typecheck` (tsc) and `lint` (Biome) all green. Every example
in the how-to was executed against the live API rather than written from memory.
