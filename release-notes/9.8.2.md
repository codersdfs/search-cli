# v9.8.2

A maintenance release: twenty-three fixes from a full static audit of the
codebase, most of them invisible until something went wrong. Nothing user-facing
was added or removed — every flag, key and command behaves as it did in 9.8.1.

## The one that mattered

A GitHub token passed as `--token` could end up in a public URL. When ghfind
crashed, it built a GitHub issue link straight from `process.argv` — argv
included your token — and opened it in a browser. The docblock claimed the
command line was redacted; it was not. Every field that reaches the issue now
goes through redaction first, and when ghfind sees a credential it prints the
URL for you to copy instead of opening a browser tab automatically.

## Security, in full

- Tokens are no longer sent to `raw.githubusercontent.com` when fetching a
  README — only to `api.github.com`, and only for a private repository.
- Skill sources and ids from the public skills.sh registry are validated before
  they can reach a shell command or a URL, so a hostile registry entry cannot
  smuggle `;`, `$(`, backticks or a path traversal into `npx skills add`.
- The config file that stores your token is now written with `0600`
  permissions. On Windows the file still inherits the directory ACL, so this
  closes the hole on POSIX only.
- `--doctor` masks the token rather than printing a raw prefix.

## Reliability

The most user-visible correctness fix: recoverable errors were treated as
crashes. The top-level catch tested `err.name === "SearchCliError"`, a string
that is never true, so a rate limit, a network blip or a layout change on
GitHub's trending page all opened a browser tab asking you to file a bug. That
branch now works, and those errors print a short explanation and exit.

`--compare` and the `ghfind_compare_repos` MCP tool both resolved repository
names through a free-text search with no `repo:` qualifier and never checked
the `fullName` that came back, so `ghfind --compare oven/bun oven-sh/bun` could
quietly compare the wrong two repositories. Both now resolve exactly.

State files — bookmarks, history, sessions, saved searches, notifications —
were written directly to their live path. A crash, a full disk, or a reader
caught mid-write left a truncated JSON file, which the loader then silently
replaced with defaults: your data was gone with no error. Writes are now atomic
(temp file plus rename).

## Smaller fixes

Notification IDs restarted after "dismiss all"; `history --delete` removed
every duplicate entry instead of one; an invalid `--sort` value degraded
silently instead of erroring; a failed "load more" in the TUI wiped the results
already on screen; `--markdown` did not escape `|` in cells while `--csv`
did; the in-memory cache was not a real LRU; local skill scanning re-walked the
filesystem on every keystroke; and skill ids containing `_` — common on GitHub
— were wrongly rejected.

## Verification

482 tests, plus `typecheck`, `lint`, `format:check` and `build` all green.
The security fixes were additionally verified with runnable probes that assert
no token substring survives URL encoding in the generated crash-report URL, that
none of twelve `raw.githubusercontent.com` requests carries an `Authorization`
header, and that seven of eight hostile skill payloads are rejected.

`README.md` test count updated to match the real suite.
